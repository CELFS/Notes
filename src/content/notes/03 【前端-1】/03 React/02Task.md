## 01 React 常识
* 区分库和框架，React 是库，而 Vue 则是框架。
  * 库的意义更像是工具、方法，根据你的需要可灵活使用，而框架倾向于定义约定俗成的规则，例如 Vue 的单文件组件推荐使用 template/script/style 三段式结构，其中 template 和 script 通常需包含有效内容（特殊场景除外），而 style 可按需省略。
  * 从结构层面，例如 Next.js 定义了基于文件系统推断的路由层级关系，并且定义了相应的入口命名与写法的一致性，但它又没有定义 React 的状态管理、服务层管理（Next 全栈）等的要求，于是，带来了相对灵活的，或者说是把定义权交给了开发者。由于 Next 是基于 React 的框架，这种特性其实源自 React 的 Hooks（函数式、组合式设计）。一方面，开发者不必遵循特定框架范式，另一方面，框架范式作为一个开放问题，变成了一种经验性的权衡取舍，反过来又直接作用在项目的维护、协作当中。

## 16 用useState实现组件函数重新执行

![image-20250812232150561](http://img.celfs.site/typora/2025/11/22/1763818362439-image-20250812232150561.png)

* 通过简单的点击 demo，JSX 改变，触发组件函数重新执行。注意，虽然组件函数已经重新执行，它却没有先恢复到默认值，而是直接显示了点击对应的值，这说明组件函数的重新执行逻辑并不是简单地将函数重新运行一次，而是有一定条件逻辑判断的，后续会展开讨论。
* State 是 react 非常重要的概念。

```jsx
import './First.css'
import { useState } from "react";


export default function First() {
  console.log(Date.now());
  const [text, setText] = useState('还没点击');
    
  return (
    <div className='main-container'>
      
      <div className='title'>
        刚点击的是-{text}
      </div>
          
      <div className='btn-container'>
        <div onClick={() => {
          setText('A')
        }}>A</div>
        <div onClick={() => {
          setText('B')
        }}>B</div>
        <div onClick={() => {
          setText('C')
        }}>C</div>
      </div>
    </div>
  );
};
```

* 特征
  * 1）整个组件函数重新执行了（想起了 Breadcrumb 使用 useCallback）；
  * 2）返回的 JSX 代码的内容发生了变化（{text} 变化）。
* 思考
  * 既然每次都是整个组件重新执行，为什么 useState 的默认值没有重置？

## 17 理解 state 是学习 Hook 的关键

![image-20250812233028038](http://img.celfs.site/typora/2025/11/22/1763818362004-image-20250812233028038.png)

* 实际上，只要数据改变，页面效果就不同，state 即状态，是一种数据，应该理解为“影响界面状态的数据”。
* state 是 react 非常的核心概念，因此状态管理则十分重要。
* 不同的数据形成不同的界面效果，**数据决定界面效果**。由此，将这种数据命名为 state 状态。

![image-20250812233516995](http://img.celfs.site/typora/2025/11/22/1763818361055-image-20250812233516995.png)

* State 的区分：组件内部、组件外部。
  * 共同点：只要 state 变化，组件函数就会重新执行，从而可能导致页面内容、结构、界面状态的改变。
  * 后续学习的所有 hook，围绕 “state 变化相关”、“组件函数重新执行的逻辑相关”，或者和这两者都有关系。因此，**在 React 中，一切都围绕 state 变化和组件重新执行来展开的**。

![image-20250812233705980](http://img.celfs.site/typora/2025/11/22/1763818360333-image-20250812233705980.png)

* 原来状态管理的重要性如此之高，之前开发的时候，只是觉得 state 的类型有点多，有时候顾不上甚至会直接将 API 返回的数据直接渲染到界面，从而跳过了将拉取的数据衔接为状态的过程，后续需要将最开始书写不规范的地方改过来。

## 18 useState 更多使用细节

![image-20251109205218688](http://img.celfs.site/typora/2025/11/22/1763818358520-image-20251109205218688.png)

* 讲解了 useState 函数的返回值，从而使用数组解构赋值获取状态数据和状态设置函数。

![image-20251109205400258](http://img.celfs.site/typora/2025/11/22/1763818358462-image-20251109205400258.png)

* 书写位置：本质就是 hook，任何 hook 都不能写在 if、for、while 等任何常规函数内部。只能写在组件函数里面，通常写在组件最顶层。
* useState 可以设置多个，任意一个对应的 state 更新逻辑，都可以让组件函数重新执行。这里提到的组件函数，即 export default function ComponentX() 这种。

* useState() 参数，任何的基本数据类型（字符串、数字、布尔）、引用数据类型（对象、数组）都可设置。相应地，状态设置函数 setState() 也同理，不同的是，状态设置函数还可以接收一个函数，相当于传入一个回调函数（重要用法）。
* 状态的更改：只能使用状态设置函数，而不能直接调用对象属性赋值。

```jsx
setData({          // 先定义对象参数
  ...data,         // 解构对象
  text1: 'hello',  // 完成赋值覆盖
});
```

* 思考
  * 为什么对象的状态设置那么麻烦，而字符串的则可以直接设置？
    * 这需要 JS 基础，这种状态设置函数在接收到数据进行处理的时候，第一件事是做对比，判断这个数据是否发生变化。
    * 对比的核心就是数据的内存地址。引用类型数据对比的核心是整体数据的内存地址，基础数据类型的对比可以理解为就是数值是否一样。
    * 因此，在处理引用类型数据的时候，要先创建一个新的对象或数组，在它内部把原来的数据取出来，这样其实整个数据就是一个新的内存地址，肯定能触发组件函数的重新执行。
    * 数据的处理方式也类似，先创建一个数组，取到原来的数组数据，其后将需要修改的索引位数据替换掉。

## 19 状态设置函数的高级用法
![image-20251109211812335](http://img.celfs.site/typora/2025/11/22/1763818358464-image-20251109211812335.png)

* 状态函数的参数设置，主要两种方式，判断当前状态数据是否存在依赖关系，比如更新状态需要基于原来的状态数据来迭代，或者完全不需要原来的状态数据而直接全新数据去赋值。

* 引用数据类型大部分情况都需要用到当前数据状态。

```jsx
import './First.css'
import { useState } from "react";


export default function First() {
    
  const [count, setCount] = useState(0);

  return (
    <div className='main-container'>
      
      <div className='title'>
        计数-{count}
      </div>
          
      <div className='btn-container'>
        <div onClick={() => {
          setCount((value) => {
            return value + 1;
          });
          setCount((value) => { // 接收上一次的状态值，可累加
            return value + 1;
          });
          console.log(count);   // 依然是 0，独立的逻辑，不要混淆
          setCount((value) => { // 类似有一种特别机制，存储了函数式的参数进行返回的值，如果需要用到状态的变量或者常量，都尽量使用这种设置方式，可以避免很多问题，尤其是当你发现获取的数据和预期的不一样时，更要注意
            return value + 1;
          });
          // 测试直观写法与预期不一致，与实际逻辑的区别
          setCount(count + 1);  // 1
          console.log(count);   // 0
          setCount(count + 1);  // 1
          console.log(count);   // 0
          setCount(count + 1);  // 1
          console.log(count);   // 0 输出时间点，依然是未更改前的值，需要理解 JS 的事件循环机制
        }}>增加</div>
      </div>
    </div>
  );
};
```

## 20 背后原理大揭秘-更彻底理解状态设置函数

![image-20251109215611018](http://img.celfs.site/typora/2025/11/22/1763818358458-image-20251109215611018.png)

* 从初始化开始，组件函数第一次执行，那么显示默认值。
* 当交互发生，执行回调，此时，一系列的设置函数并非立即更新组件数据，而是存在一个更新意图机制，即存在一个特别数据，每次执行都把传入的参数放入其中，形成更新意图队列，具体的处理就称为调度，由 React 机制自行决定，通常放在当前周期循环的最后，简单来说，就是尽快执行，但不是立马执行。

![image-20251109220725254](http://img.celfs.site/typora/2025/11/22/1763818358459-image-20251109220725254.png)

![image-20251109221227327](http://img.celfs.site/typora/2025/11/22/1763818358455-image-20251109221227327.png)

![image-20251109221635847](http://img.celfs.site/typora/2025/11/22/1763818358452-image-20251109221635847.png)

* 将更新意图队列中的每个表达式算出，将最后一个值（示例为 100）用于状态对比，从而决定是否更新状态数据。
* 因此，在第一次组件函数执行，到第二次组件函数重新执行，传入新的状态数据值之前，整个过程的原有状态还是初始值。因此，上一节的 count 值一直是 0，因为真正的值更新需要在更新意图队列计数之后。

## 21 不是所有数据都要处理成状态数据

* 绝大部分数据不需要处理为状态数据，除非满足两个特征
  * 1）将来有可能发生变化；
  * 2）变化会影响页面内容或样式、结构。

* 原则：如果一个值可以通过已有的状态或 props 计算出来，那么它就不需要成为独立的状态。不轻易创建新的状态数据，如果这个数据能间接获取就间接获得。
* 关于什么时候需要设置状态数据，可以在代码实践中逐渐感悟，允许开始的容错空间。

## 25 组件函数重新执行导致的问题

* 前面了解了 useState 与 uesReducer 两个 hook，但有这样一个场景
  * 1）数据不需要展示在界面上；
  * 2）不希望这个数据的变化让组件重新执行。

![image-20251114022930928](http://img.celfs.site/typora/2025/11/22/1763818358400-image-20251114022930928.png)

* 思考
  * 值得注意的是，状态数据的改变，每次都触发组件重新执行、重新渲染。从而导致一些作用域范围内的数值一直被初始化，就无法实现累积的效果了。而如果我们在组件函数前面定义组件内的全局变量，当这个组件被复用的时候，那么这个全局变量并不会像预期的在组件内部自己维护，而会变成在组件之间累加。
  * 文件在引入之后，其实已经被执行了，这些相关的内容已经在内存当中，只是还没有被调用，没有产生组件对应的实例。因此，在组件函数前面定义的变量，其实也已经被加载到内存中。
  * 组件实例内部代码的逻辑，访问到的都是组件内，我们写在组件函数外的同一个变量。因为组件函数内部没有同名变量，因此通过作用域链访问到的就是组件函数外部的变量。本质就是从组件内部沿着作用域链到了组件外部的代码。
  * 因此，需要有一种方式，能够把数据放在组件函数内部，从而实现每个组件实例都有独立的、隔离的一份数据的场景。
